# 폴리싱 단계 작업 순서

> `design.md` 0~10단계 구현이 모두 끝난 뒤의 작업을 다룬다.
> 이 문서는 **작업 순서를 강제하기 위한 것**이다. 순서를 바꾸지 말 것.

---

## 이 단계의 목표

기능 검증용 프로토타입을 **"게임다운 플레이 빌드"** 로 다듬는다.
새로운 게임 규칙을 추가하는 단계가 **아니다.**

---

## 작업 순서

| 순서 | 작업 | 성격 |
|---|---|---|
| **P1** | 프리팹 값 덤프 + 낡은 기록 정리 | 안전망 |
| **P2** | 에셋 교체 및 비주얼 정리 | 게임 규칙 불변 |
| **P3** | 레벨 디자인 매뉴얼 작성 | 문서 |
| **P4** | 플레이 데이터 수집 | 사람이 진행 (P2와 병행 가능) |
| **P5** | 밸런스 조정 | 데이터 기반 |
| **P6** | 연출 폴리싱 + 빌드 | 위가 확정된 뒤 |

### 왜 이 순서인가

- **에셋 교체가 연출보다 먼저인 이유**: 에셋을 리임포트하면 프리팹 구조가 초기화된다(실제로 겪은 문제, 원인은 사용자의 수동 리임포트로 확인됨). 연출을 먼저 붙이면 파티클·머티리얼 설정이 같이 날아간다.
- **밸런스가 연출보다 먼저인 이유**: 밸런스가 바뀌면 튜토리얼 강제 슬롯 위치(타일 인덱스)도 재계산해야 한다. 연출을 먼저 붙이면 두 번 일한다.
- **데이터 수집이 먼저인 이유**: 현재 `PlayStats.csv`는 0줄이다. 지금 밸런스를 손대면 근거 없이 감으로 고치는 것이 된다.
- **매뉴얼이 P3인 이유**: P1 덤프 결과와 P2에서 확정된 에셋을 반영해야 한다. 더 미루면 밸런스 조정(P5) 때 정작 필요한 문서가 없다.

---

## ⛔ 이 단계에서 하지 않을 것

아래는 **P4가 끝난 뒤에 별도로 기획한다.** 지금 착수하지 말 것.

- 캐릭터 스킬 (스퍼트 등)
- 새로운 길 종류 / 경로 타입
- 스테이지 등급제, 보상, 메타 프로그레션
- 스테이지 추가

> 이유: 이것들은 전부 게임 규칙을 바꾼다. 특히 스킬은 "재화가 부족해서 포기해야 한다"는
> 핵심 전제를 흔들어서, `design.md` 10장 검증 의도 ①의 기대값부터 다시 잡아야 한다.
> 기반 밸런스가 확정되기 전에 얹으면 "재미있어진 건지 망가진 건지" 구분할 수 없다.

## P1 — 프리팹 값 덤프 + 낡은 기록 정리

에셋 교체로 프리팹이 초기화됐을 때 **복구 기준**으로 쓸 기록을 먼저 남긴다.

### 1-1. 프리팹 값 덤프

아래 프리팹 전부에 대해 값을 텍스트로 뽑아 `PROGRESS.md`에 기록한다.

| 프리팹 | 비고 |
|---|---|
| `Fox` | 플레이어 |
| `Chicken` | 기본형 몬스터 |
| `Monster_AreaType` | 광역형 (색상 틴트 placeholder) |
| `Monster_DPSType` | 고DPS형 (색상 틴트 placeholder) |
| `Projectile_Egg` | 투사체 |
| `Wall` | 벽 |

각 프리팹에서 다음을 빠짐없이 기록할 것.

- **루트**: 이름 / Tag / Layer / Transform(position·rotation·**scale**)
- **Model 자식**: 오브젝트 이름 / 로컬 Transform / 참조하는 메시·머티리얼 에셋 경로
- **Collider**: 종류 / Radius / Height / Center / IsTrigger
- **Rigidbody**: useGravity / isKinematic (있는 경우)
- **NavMeshAgent**: Radius / Height / Base Offset / Speed / Angular Speed / Acceleration / Stopping Distance
- **Animator**: 참조 컨트롤러 에셋 / Avatar 설정
- **`MonsterTower`**: attackRange / attackCooldown / attackDamage / 그 외 인스펙터 필드 전부
- **`FogVisibility`**: visionRadius
- **`AttackRangeIndicator`**: visionRadius / 선 굵기·색 등 표시 설정
- **`Projectile`**: 속도 / 유지시간 / 레이어 마스크 값
- 그 외 붙어 있는 모든 컴포넌트와 그 인스펙터 값

> ⚠️ **Layer와 scale을 특히 정확히 적을 것.**
> `Projectile_Egg`의 Layer가 `Default`가 아니면 자기 자신을 벽으로 오검출한다.
> `Chicken`/`Projectile_Egg`의 루트 scale은 (2,2,2)이며, 초기화되면 (1,1,1)로 돌아간다.

### 1-2. 씬 배치 값 덤프

프리팹 외에 씬에만 있는 값도 함께 기록한다.

- 두 씬(`Stage1(Test)`, `Stage2`)의 몬스터 배치 좌표 전부
- 각 씬의 `CurrencyManager.totalCurrency` (스테이지1=6, 스테이지2=7)
- 각 씬의 `visionRadius` (스테이지1=8, 스테이지2=5) — 몬스터마다, 그리고 `FogGround`까지
- `TutorialManager`의 강제 슬롯 값 (현재 타일3 Left)

### 1-3. 낡은 기록 정리

`PROGRESS.md`에 실제 구현과 어긋나는 기록이 남아 있다. 아래를 수정할 것.

| 대상 | 수정 내용 |
|---|---|
| 3단계 검증 게이트 | "벽 있음: **발사 자체가 안 됨**" → 현재 방식은 "몬스터는 항상 발사하되 투사체가 벽에 막혀 소멸"이다. 이 기준으로 다시 기록 |
| 0단계 검증 게이트 | "Fox 재검증 필요" 표시 제거 — 실제 마우스 플레이로 확인 완료됨 |
| `OnAttackHit` Animation Event 항목 | 공격 애니메이션을 쓰지 않기로 확정했으므로 무효 기록임을 명시 |
| 테스트 씬 Monster 좌표 (-6,0,11) | `Monster_A~D`로 대체되어 폐기된 값임을 명시 |
| 프리팹 초기화 이슈 | 원인 확인됨 — 사용자의 수동 FBX 리임포트가 원인. Unity/MCP 버그 아님 |

## P2 — 에셋 교체 및 비주얼 정리

> 교체할 에셋은 사용자가 준비해 온다. **어떤 에셋을 쓸지 임의로 정하지 말 것.**

### 절차

1. 에셋 임포트
2. **머티리얼을 URP 셰이더로 변환** (`Universal Render Pipeline/Lit`) — 안 하면 분홍색으로 깨진다
3. 리깅 타입 확인 (Humanoid / Generic) — 기존 `Fox`/`Chicken`은 둘 다 **Generic / No Avatar**
4. 프리팹의 **`Model` 자식만 교체.** 루트의 컴포넌트 구성은 유지
5. P1에서 덤프한 값과 대조해 **초기화된 항목이 있으면 전부 복구**
6. 새 모델 크기에 맞춰 Collider·NavMeshAgent 수치 재조정
7. Animator Controller 연결 — 파라미터는 기존과 동일하게 `IsMove`(Bool) / `Die`(Trigger)

### 교체 후 반드시 확인할 것

- [ ] 루트 Layer / Tag가 유지되는가 (`Fox` → Tag `Player`, Layer `AttackTarget`)
- [ ] `Projectile_Egg`의 Layer가 `Default`인가
- [ ] 루트 scale이 유지되는가
- [ ] 모델의 정면 방향(±Z)이 맞는가
- [ ] `MonsterTower` 수치가 유지되는가
- [ ] `FogVisibility` / `AttackRangeIndicator`의 `visionRadius`가 씬 값과 맞는가
- [ ] 두 씬 모두에서 확인했는가

### 환경 에셋을 추가하는 경우

- 레이어는 반드시 **`Default`**. `WallVision`에 올리면 장식물이 투사체를 막아 핵심 규칙이 무너진다
- `FogVisibility` 컴포넌트를 붙이고 `visionRadius`를 해당 씬 값에 맞출 것 (안 붙이면 안개 위로 튀어나와 보인다)
- 경로 타일 위에 두지 말 것. NavMesh 재베이크 후 Player 이동이 막히지 않는지 확인
- 배치 범위는 `Floor`(30×60) 안쪽 — 밖에 두면 안개가 덮지 않는다
- 임시로 깔아둔 `PathTile_00~19`(황토색 Plane)는 정식 경로 비주얼이 생기면 정리 대상

## P3 — 레벨 디자인 매뉴얼 작성

> 사용자가 **"이걸 하려면 뭘 만지면 되지?"** 를 찾아볼 수 있는 실무 매뉴얼.
> 설계 이론이나 배경 설명은 넣지 말 것. **작업 방법만** 쓴다.
> 결과물은 `docs/level-design.md` 한 파일.

### 형식

작업 단위로 나누고, 각각을 이렇게 쓴다.

```
## 길을 한 칸 늘리고 싶다

1. Hierarchy에서 Path > Tile_19 선택, Ctrl+D로 복제
2. 이름을 Tile_20으로 변경
3. Position을 이전 타일에서 진행 방향으로 2유닛 이동한 값으로 설정
4. 벽 슬롯도 같이 추가해야 함 → "벽 슬롯을 추가하고 싶다" 참조

⚠️ 타일은 Path의 자식 순서대로 읽히므로, Hierarchy에서 순서가 맞아야 함
```

### 다뤄야 할 작업 목록

**길 관련**
- 길을 늘리거나 줄이고 싶다
- 길을 꺾고 싶다 (코너 만들기)
- 길 전체를 다른 모양으로 새로 깔고 싶다

**벽 슬롯 관련**
- 벽 슬롯을 추가하고 싶다
- 벽 슬롯 위치를 옮기고 싶다
- 코너에서 슬롯이 길 위에 겹친다

**몬스터 관련**
- 몬스터를 추가하고 싶다
- 몬스터 종류를 바꾸고 싶다
- 몬스터 사거리·공격력을 바꾸고 싶다
- 몬스터가 특정 구간만 위협하게 하고 싶다

**수치 관련**
- 벽(재화) 개수를 바꾸고 싶다
- 시야 범위를 바꾸고 싶다
- 플레이어 체력·이동속도를 바꾸고 싶다

**스테이지 관련**
- 새 스테이지를 만들고 싶다
- 튜토리얼 문구나 순서를 바꾸고 싶다
- 튜토리얼에서 벽을 세우라고 지정하는 위치를 바꾸고 싶다

### 쓸 때 지킬 것

- **클릭 경로를 생략하지 말 것.** "Inspector에서 값을 바꾼다"가 아니라 "Hierarchy에서 X 선택 → Inspector의 Y 컴포넌트 → Z 값 수정"
- **실제 현재 값을 확인해서** 쓸 것. 기억이나 옛 문서를 믿지 말 것
- 놓치면 안 되는 것만 `⚠️`로 한 줄 경고. 예: 시야 범위는 세 군데를 다 바꿔야 함, 새 씬에는 EventSystem이 있어야 함
- 길어지면 안 됨. 한 작업당 **5~6줄 이내**를 목표로

### 맨 뒤에 붙일 것

**오브젝트 한눈에 보기** — 씬에 있는 것들이 각각 뭔지 한 줄씩. 표 하나로 충분하다.

| 오브젝트 | 뭐 하는 것 | 자주 만지는 값 |
|---|---|---|
| (예) `Managers > CurrencyManager` | 벽 개수 관리 | `totalCurrency` |

**새 스테이지 만든 뒤 확인할 것** — 체크박스 5~6개.
경로 끝까지 이동 / 벽 배치 / 클리어·실패 / 재도전 버튼 / 안개가 따라옴 정도.

- P2와 병행 가능 (에셋과 무관)

## P5 — 밸런스 조정

`PlayStats.csv` 데이터가 쌓인 뒤 `design.md` 10.4 기준과 비교해 조정한다.

| 기대값 | 기준 |
|---|---|
| 남은 재화 | 0~1개 |
| 남은 체력 | 30~70% |
| 반응 시간 | 1.5~3초 (스테이지2만) |

> ⚠️ `visionRadius`를 바꾸면 **세 컴포넌트 전부**(`FogVisibility` / `AttackRangeIndicator` / `FogOfWarGround`)를 맞출 것.
> ⚠️ 몬스터 배치나 재화량을 바꾸면 `TutorialManager`의 강제 슬롯 값도 재계산해야 한다.

## P6 — 연출 폴리싱 + 빌드

### 연출
`tutorial.md` 5장에 이미 기획되어 있다. 새로 기획할 필요 없이 그대로 구현하면 된다.
범위는 사용자가 지정한다 — 임의로 전부 착수하지 말 것.

### 빌드 전 처리

- [ ] `PlayStats.csv` 경로를 `Application.dataPath/..` → **`Application.persistentDataPath`** 로 변경
      (빌드에서는 실행 파일 위치가 기준이 되어 쓰기 권한 문제가 생길 수 있음)
- [ ] `WallPlacementManager`에 디버깅용으로 넣은 `Debug.Log` 제거
- [ ] 미사용 파일 확인 — `TutorialPopupManager.cs` / `MonsterTutorialTrigger.cs`는 더 이상 쓰지 않음
      (삭제는 사용자 확인 후)
