# 리버스 타워디펜스 — 프로토타입 설계 문서

> Claude Code 작업용 설계서.
> 학교 과제(게임엔진 응용 프로그래밍) 제출용 프로토타입이며, **수업에서 다룬 기능을 응용·조합해 새로운 플레이 경험을 만드는 것**이 핵심 요건이다.
> 새 기능을 화려하게 추가하기보다, 기존 기능의 **주체와 목적을 뒤집는** 방향으로 접근한다.
> 작업 방식·금지 사항은 `CLAUDE.md` 참조.

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 엔진 | Unity 6000.3.9f1 |
| 장르 | 리버스 타워디펜스 · 스테이지형 최적화 퍼즐 |
| 한 줄 컨셉 | 정해진 길을 자동으로 걸어가는 내 캐릭터를, 한정된 재화로 세운 벽으로 지켜내는 게임 |
| 핵심 재미 | 제한된 자원 안에서 "무엇을 막고 무엇을 포기할 것인가"를 순간적으로 판단하는 긴장감 |
| 플레이어 조작 | **이동 조작 없음.** 캐릭터는 경로를 따라 자동 이동. 유저는 오직 벽 배치만 조작 |
| 범위 | 스테이지 2개(튜토리얼 + 본 시연)짜리 데모 프로토타입 |

## 2. 핵심 메커니즘 (가장 중요)

수업 프로젝트에는 **"벽 너머의 대상 제외"** 기능이 있다.
원래 용도: *Player가 자동 공격할 때, 벽에 가려진 Monster는 공격 대상에서 제외한다.*

이 게임은 이것을 **정반대로 뒤집는다.**

> **플레이어가 세운 벽이 Monster의 공격을 막아낸다.**

이 한 줄이 게임 전체의 출발점이다. 구현 시 이 판정이 가장 먼저 동작해야 하며,
"벽을 세우면 안 맞는다"는 루프가 검증되기 전에 다른 기능을 붙이지 말 것.

> **차단 방식 (확정, 초기 설계에서 변경됨)**
> 몬스터는 벽 유무와 상관없이 사거리 안이면 **항상 발사한다.** 벽은 발사를 막는 것이 아니라,
> 날아가는 **투사체를 물리적으로 막는다.** 투사체가 벽 레이어와 충돌하면 그 자리에서 피해 없이 소멸한다.
> 초기 설계는 "발사 전 Raycast로 시야를 검사해 발사 자체를 취소"하는 방식이었으나,
> 투사체가 벽에 맞고 사라지는 시각적 피드백이 더 낫다고 판단해 변경했다. **되돌리지 말 것.**

### 주체 반전 요약

| 기존 (수업) | 이 게임 |
|---|---|
| Player가 Monster를 탐색 → 자동 공격 | **Monster가 Player를 탐색 → 자동 공격** |
| Player는 유저 입력으로 이동 | **Player는 목적지까지 자동 이동** |
| 벽은 Player의 공격을 막음 | **벽은 Monster의 공격을 막음** |

## 3. 게임 규칙 (확정 사항)

### 3.1 경로와 타일
- 경로는 **타일(칸) 단위**로 분할된다.
- Player는 타일을 순서대로 자동 통과한다.
- 각 타일에는 **좌/우 사이드에 벽 슬롯이 1개씩** 존재한다.

### 3.2 벽
- **단일 종류, 동일 비용.** 벽 종류를 나누지 않는다.
- **벽 1개 = 정확히 그 타일 1칸만 차단.** 인접 칸에 대한 부분 차폐는 없다.
- **파괴되지 않는다.** 내구도 개념 없음. 한 번 세우면 스테이지 종료까지 유지.
- **Player의 이동 경로에는 영향을 주지 않는다.** NavMesh를 갱신하지 않으며, 오직 투사체를 막는 전용 레이어(`WallVision`)로만 동작한다. ← **중요**
- 이 레이어에는 **벽만** 올린다. 투사체나 환경 장식물이 올라가면 핵심 규칙이 무너진다.

### 3.3 재화
- 스테이지 시작 시 **고정 총량을 한 번에 전액 지급.** 시간에 따라 누적되지 않는다.
- 벽 배치 시마다 차감.

### 3.4 배치 제약
- **Player의 현재 타일보다 앞쪽 타일의 슬롯에만 배치 가능.** 이미 지나간 타일은 잠긴다.
- 게임 진행 중 실시간으로 배치한다. (사전 배치 단계 없음)

### 3.5 몬스터
- **타워디펜스의 "타워" 역할.** 고정 위치에서 탐지·공격만 반복한다. 이동/추적 없음.
- **원형 사거리(반지름)만 사용.** 공격 각도 판정은 사용하지 않는다.
- Player는 **몬스터를 반격할 수단이 없다.**
- 공격은 **투사체 발사** 방식. (기존 투사체 기능 그대로 재사용)
- 공격 쿨다운마다 판정하므로, **사거리 안에 오래 머물수록 여러 번 맞는다.**

### 3.6 몬스터 3종

| 타입 | 사거리 | 쿨다운/공격력 | 역할 |
|---|---|---|---|
| 기본형 | 보통 | 보통 / 보통 | 기준점, 튜토리얼용 |
| 광역 사거리형 | 큼 | 보통 / 낮음~보통 | 많은 칸을 얕게 위협. 전부 막으면 재화 소모가 큼 |
| 고DPS형 | 좁음 | 짧음 / 높음 | 적은 칸이지만 안 막으면 급격히 위험. 우선 차단 대상 |

> 3종은 **같은 스크립트에 파라미터만 다르게** 넣어 프리팹으로 분화한다. 별도 클래스를 만들지 말 것.

### 3.7 시야 제한 (핵심 재미 장치)
- **Player를 중심으로 한 원형 반경(`visionRadius`, 월드 유닛)** 안에 들어온 것만 보인다. (초기 설계의 타일 개수 기반 방식은 폐기)
- 시야 안에 들어오면 **몬스터 본체와 사거리 표시가 함께** 드러난다. 경로 자체는 항상 보인다.
- 한 번 드러난 몬스터는 계속 보인다(영구 공개). 바닥 안개도 지나간 자리가 영구히 걷힌다.
- 이유: 전체 맵이 다 보이면 "미리 계산해서 배치하고 관전"하는 게임이 되어버린다. 정보를 제한해야 순간 판단이라는 재미가 생긴다.
- `반응 시간 = visionRadius ÷ 이동 속도` — 난이도의 핵심 손잡이.

> ⚠️ `visionRadius`는 `FogVisibility` / `AttackRangeIndicator` / `FogOfWarGround` 세 컴포넌트가 **각각 개별로** 들고 있다. 값을 바꿀 때는 반드시 세 군데를 함께 맞출 것.

### 3.8 승패 조건
- **성공:** Player가 도착 지점에 체력 1 이상으로 도달
- **실패:** 이동 중 체력 0 이하
- **재도전:** 재화 총량·몬스터 배치·경로를 **동일하게** 리셋 (죽으면서 외우는 학습 루프)

## 4. 밸런스 공식

```
재화(B) = N_필수 + α × N_선택
```

| 변수 | 의미 |
|---|---|
| `N_필수` | 고DPS형이 위협하는 타일 수 총합 — 사실상 반드시 막아야 하는 칸 |
| `N_선택` | 광역형이 위협하는 타일 수 총합 — 일부만 막아도 생존 가능한 칸 |
| `α` | 0.4~0.7. 선택차단분 중 감당 가능한 비율. 스테이지가 어려워질수록 낮춘다 |

**생존 보장 조건:**
```
(N_선택 − α × N_선택) × 광역형 한 칸당 평균 피해 ≤ Player 최대체력 × 0.7~0.8
```

> 무피해 클리어가 불가능하도록 설계한 것은 **의도적**이다. "얼마나 적게 맞고 통과했는가"가 자연스러운 스코어가 된다.

## 5. 스크립트 구조 (제안)

기존 수업 프로젝트의 스크립트를 최대한 재사용하고, 아래는 **새로 만들거나 수정할 것**만 정리한다.

### 5.1 타일 · 경로

```
TileData            // 타일 1칸의 데이터
  - int index
  - Vector3 worldPosition
  - bool leftSlotOccupied
  - bool rightSlotOccupied

PathManager         // 타일 배열 보유, 경로 전체 관리
  - TileData[] tiles
  - int GetTileIndexAt(Vector3 worldPos)
  - bool CanPlaceAt(int tileIndex)   // Player 현재 인덱스보다 앞인지 검사
```

### 5.2 Player

```
PlayerAutoMover     // 기존 이동 스크립트 수정 — 입력 제거
  - 타일을 0→1→2… 순서대로 웨이포인트 삼아 NavMeshAgent 목적지를 갱신
    (최종 목적지만 지정하면 평지에서 직선으로 가버려 타일·꺾인 경로가 무의미해짐)
  - 매 프레임 현재 타일 인덱스 갱신 → PathManager에 전달
    ※ "현재 타일" = 마지막으로 도달한 타일(목표 타일 - 1)
  - 매 프레임 agent.velocity로 Animator의 IsMove 갱신
  - 체력 0이면 이동 정지 (기존 "Player 행동 중지" 재사용)

PlayerHealth        // 기존 체력/사망 스크립트 재사용
  - 체력 0 → GameOver 이벤트 발행
```

### 5.3 벽 · 재화

```
WallSlot            // 타일 좌/우에 하나씩. 클릭 대상
  - int tileIndex
  - SlotSide side (Left/Right)
  - OnClick() → WallPlacementManager에 배치 요청

WallPlacementManager
  - 배치 가능 여부 검사 (재화 충분 + PathManager.CanPlaceAt)
  - 벽 프리팹 생성, 재화 차감
  - 벽은 투사체 차단 전용 레이어(WallVision)로 생성 (NavMesh 갱신 금지)

CurrencyManager
  - int totalCurrency (스테이지 시작 시 전액 지급)
  - bool TrySpend(int amount)
  - UI 갱신 이벤트
```

### 5.4 몬스터

```
MonsterTower        // 기존 Monster 스크립트를 고정형으로 개조
  - float attackRange       // 원형 사거리 (인스펙터 노출)
  - float attackCooldown    // 인스펙터 노출
  - float attackDamage      // 인스펙터 노출
  - 매 프레임: 사거리 안 대상 탐지 → 있으면 그쪽을 향해 Y축 회전
  - 쿨다운마다:
      1) 거리 검사 (원형, 각도 판정 없음)
      2) 대상이 있으면 투사체 발사 ← 벽 검사는 하지 않는다 (2장 참조)
      3) 없으면 기존 "대상 재탐색 대기"로 다음 쿨다운까지 대기

Projectile          // 벽 차단을 담당하는 쪽
  - 발사 시점에 방향을 한 번 계산해 직선 이동
  - FixedUpdate마다 이번 프레임 이동 구간을 SphereCast로 사전 검사
    (고속 이동 시 OnTriggerEnter는 벽을 그냥 통과해버림 — 터널링)
  - 벽 레이어와 충돌 → 피해 없이 소멸 / 대상 레이어와 충돌 → IDamageable.TakeDamage
  - 자기 자신을 오검출하지 않도록 자기 반지름만큼 앞에서부터 캐스트
```

> **주의:** 몬스터에 추적(NavMesh) 로직을 남겨두지 말 것. 고정형이다.
> **주의:** 투사체 프리팹의 레이어는 반드시 `Default`. 벽 레이어에 올리면 자기 자신을 벽으로 오검출한다.

### 5.5 카메라 · 스테이지

```
FogVisibility        // 시야 밖 오브젝트를 숨김 (범용 — 몬스터·환경물 공용)
  - Player와의 거리가 visionRadius 밖이면 자식 Renderer 전부 비활성화
  - 한 번 드러나면 영구 유지

AttackRangeIndicator // 몬스터 사거리를 바닥에 원으로 표시
  - LineRenderer로 attackRange 반경을 그림, 시야 안일 때만 표시

FogOfWarGround       // 바닥 전체를 덮는 안개를 텍스처로 실시간 제거
  - Player 주변 원형 영역의 알파를 0으로 지움, 걷힌 자리는 영구 유지

※ 위 세 컴포넌트는 모두 LateUpdate에서 Player 위치를 읽는다.
  Update에서 읽으면 NavMeshAgent 이동 전 위치를 잡아 한 프레임 밀린다.
※ Cinemachine 카메라의 Damping은 (0,0,0). 카메라가 지연 추적하면
  화면상 캐릭터와 안개 경계가 어긋나 보인다.

StageManager
  - 스테이지 시작: 재화 지급, Player 초기화, 몬스터 배치
  - 클리어 판정 (도착 지점 도달)
  - 실패 판정 (PlayerHealth의 GameOver 이벤트 수신)
  - 재도전: 동일 조건으로 전체 리셋
```

## 6. 스테이지 구성

| 스테이지 | 목적 | 구성 |
|---|---|---|
| **1. 튜토리얼** | 기본 루프 압축 학습 | 기본형 1~2마리, 겹침 구간 1곳, 넉넉한 시야, 여유 있는 재화 |
| **2. 본 시연** | 핵심 재미 전달 | 3종 전부 등장, 중첩 다수, 좁은 시야, 빠듯한 재화(일부 포기가 필연) |

> ⚠️ 스테이지를 조립할 때 **10장의 검증 의도를 함께 볼 것.** 재화 총량과 `visionRadius`가 곧 검증 대상이므로, 나중에 측정했을 때 의미 있는 결과가 나올 수 있는 구성이어야 한다.

## 7. 구현 순서 (이 순서대로 진행할 것)

스크립트 작성부터 에디터 조작까지 각 단계를 끝까지 완료한 뒤 다음으로 넘어간다.
단계를 건너뛰지 말 것 — 0단계(에셋 적용)를 먼저 끝내야 하고, 3단계까지 끝나야 이 게임이 재미있는지 알 수 있다.

### 0단계 — 프로젝트 셋업 & 에셋 임포트
> 빈 프로젝트에서 시작한다. 로직 작업에 들어가기 전에 이 단계를 완전히 끝낼 것.

> ### 사용 캐릭터 에셋
>
> | 에셋 | 용도 |
> |---|---|
> | `Fox` | **Player(플레이어 캐릭터)** |
> | `Chicken` | **Monster(고정형 타워 몬스터)** |
> | `Projectile_Egg` | 몬스터가 발사하는 **투사체** |
>
> 에셋 원본 파일 이름은 **그대로 유지한다.** 리네임 금지 (참조가 깨질 위험).

**1) 프로젝트 생성 및 패키지 설치**
- URP 템플릿으로 Unity 프로젝트 생성 (Unity 6.3 LTS)
- 필요한 패키지 설치: **Input System**, **Cinemachine**, **AI Navigation(NavMeshSurface)**
- 폴더 구조 생성: `Assets/Scripts/`, `Assets/Prefabs/`, `Assets/Scenes/`

**2) 캐릭터 에셋 임포트**
- 캐릭터 에셋 임포트 후 머티리얼을 **URP 셰이더로 변환** (Built-in 셰이더는 분홍색으로 깨짐)
- 리깅 타입 확인 (Humanoid / Generic) — Animator 구성 방식이 달라짐

**3) 프리팹 제작**
아래 구조로 프리팹을 만든다. 로직 컴포넌트는 루트에, 시각적 모델은 자식으로 분리한다.

```
Player (루트)  ← Player 스크립트, NavMeshAgent, Collider
└─ Model       ← 에셋의 Fox 모델 + Animator

Monster (루트) ← Monster 스크립트, Collider (NavMeshAgent 불필요 — 고정형)
└─ Model       ← 에셋의 Chicken 모델 + Animator

Projectile (루트) ← 투사체 스크립트, Collider(Trigger), Rigidbody
└─ Model          ← 에셋의 Projectile_Egg 모델
```

- 이 Model 분리 구조를 지킬 것. 이후 단계에서 피격 시 Material 변경, 이동 방향 바라보기 등이 Model 자식을 대상으로 동작한다
- Animator Controller 구성 (대기 / 이동 / 사망)
  - ⚠️ **공격 애니메이션은 사용하지 않기로 확정했다.** 몬스터는 모션 없이 투사체만 발사한다. Attack 상태와 타격 프레임 Animation Event는 만들지 않는다.
- 모델 크기·정면 방향(±Z) 확인, NavMeshAgent의 Radius/Height를 캐릭터 크기에 맞게 조정
- 투사체(계란) 크기가 캐릭터 대비 적절한지 확인

**4) 기본 씬 구성**
- 바닥(Plane 등)과 테스트용 경로 배치
- NavMeshSurface 추가 후 베이크
- 레이어 생성: 공격 대상 구분용, **벽 투사체 차단 전용 레이어** (design.md 3.2 참조)
- Cinemachine 탑뷰 카메라 리그 구성

**✅ 검증 게이트**
- 씬에 Player/Monster 프리팹을 배치하고 재생 → 모델이 정상적으로 보이고, 애니메이션이 재생되고, NavMesh 위에서 이동 가능한지 확인
- **플레이어가 `Fox` 모델로, 몬스터가 `Chicken` 모델로 나오는지 눈으로 확인할 것**
- 여기서 확인하고 넘어가야 이후 문제가 셋업 탓인지 새 로직 탓인지 구분할 수 있다

### 1단계 — 경로·타일 데이터 구조
- `TileData`, `PathManager` 작성
- `PlayerAutoMover` 작성 (목적지 자동 고정 + 타일 인덱스 갱신)
- 씬에 경로 타일 배치, Player에 스크립트 연결, NavMesh 베이크
- 타일 그리드가 실제 경로와 정렬되는지 확인

### 2단계 — 벽 배치 & 재화
- `WallSlot`, `WallPlacementManager`, `CurrencyManager` 작성 (앞쪽 타일 제약 검사 포함)
- 타일마다 좌/우 슬롯 오브젝트 생성·배치
- 벽 프리팹 생성, **투사체 차단 전용 레이어** 설정
- 재화 표시 UI 구성 및 바인딩

### 3단계 — 몬스터 반전 로직 ★핵심
- `MonsterTower` 작성 (탐색 주체 반전 + 원형 사거리 + 기존 쿨다운/재탐색 연결)
- `Projectile`에 벽 충돌 차단 구현 (2장 "차단 방식" 참조)
- 몬스터 프리팹 생성 및 스크립트 연결
- 투사체 발사 위치·충돌 대상을 Player로 재설정
- **✅ 검증 게이트:** 여기서 "벽 세우면 안 맞는다"가 실제로 동작해야 한다. 안 되면 다음 단계로 넘어가지 말 것.
  - 통과 기준: 벽이 있으면 투사체는 계속 발사되지만 벽에 맞고 소멸해 Player에게 피해가 들어가지 않는다.

### 4단계 — 체력·피격 표현

## 9. 설계상 주의사항

> 작업 방식·금지 사항 등 일반 규칙은 `CLAUDE.md` 참조. 여기서는 이 게임의 설계에 관한 것만 다룬다.

1. **기능의 개념을 재현하는 것이 과제 요건이다.** 수업에서 다룬 기능(이동, 자동 공격, 대상 탐색, 벽 너머 대상 제외, 체력/사망, 피격 표현 등)의 **동작 방식과 구조를 새로 구현**한다. 어떤 기능이 있어야 하는지는 `reference.md` 1번 섹션 참조.
2. **벽은 NavMesh를 갱신하지 않는다.** Player 경로에 영향을 주면 게임이 망가진다. 투사체 차단 전용 레이어(`WallVision`)로만 동작시킬 것.
3. **`WallVision` 레이어에는 벽만 올린다.** 투사체가 올라가면 자기 자신을 벽으로 오검출하고, 환경 장식물이 올라가면 벽이 아닌 것이 공격을 막게 되어 핵심 규칙이 무너진다.
4. **몬스터는 각도 판정을 쓰지 않는다.** 원형 사거리만.
5. **몬스터는 이동하지 않는다.** 추적 로직을 남기지 말 것.
6. **입력은 New Input System으로만 처리한다.** 프로젝트가 Input System Package 전용 설정이라 legacy `OnMouseDown` 등은 동작하지 않는다.
7. 수치(시야 거리, 이동 속도, 사거리 등)는 **일단 대충 넣고 플레이 테스트하며 조정**한다. 초반부터 정밀 밸런싱하지 말 것.

## 10. 기획 의도 검증

> **구현은 10단계에서 한다. 9단계까지는 이 장을 "스테이지를 어떻게 설계해야 하는지"의 참고 자료로만 볼 것.**
> 이 게임에서 실제로 어긋날 가능성이 있는 두 가지 전제를 데이터로 확인한다.

### 10.1 검증 의도 ① — 재화 밸런스

**전제:** "재화가 부족해서 전부 막을 수 없고, 무엇을 포기할지 고민하게 된다." (4장 밸런스 공식의 뿌리)

어긋나는 두 방향:
- 재화가 남아돌면 → 다 막고 무피해 클리어 → 선택의 딜레마가 사라짐
- 재화가 너무 적으면 → 어떻게 배치해도 죽음 → 최적화가 아니라 운

| 구분 | 내용 |
|---|---|
| 정량 지표 | 클리어 시 남은 재화 / 남은 체력 / 배치한 벽 개수 / 위협 타일 총 개수 |
| 기대값 | 남은 재화 **0~1개**, 남은 체력 **30~70%** |
| 정성 설문 | "벽을 세울 곳을 고를 때 고민이 되었나요?" — 고민 없었다 / 적당했다 / 너무 빠듯했다 |

### 10.2 검증 의도 ② — 정보 제한

**전제:** "시야를 제한했기 때문에 순간 판단이 필요하다." (3.7의 근거)

어긋나는 두 방향:
- 시야가 넓으면 → 미리 다 보고 배치 → 정보 제한이 무의미해짐
- 시야가 좁으면 → 반응할 시간 자체가 없음 → 불합리하게 느껴짐

| 구분 | 내용 |
|---|---|
| 정량 지표 | 몬스터가 시야에 들어온 시점 ~ 해당 위협에 벽을 배치한 시점까지의 시간 / 위협을 인지하고도 막지 못하고 지나친 타일 수 |
| 기대값 | 반응 시간 **1.5~3초** (`visionRadius ÷ 이동속도` 계산값과 비교) |
| 정성 설문 | "위협을 발견하고 대응할 시간이 충분했나요?" — 촉박했다 / 적당했다 / 너무 여유로웠다 |

### 10.3 기록 방식

- `PlayStatsLogger` 하나가 위 지표를 모두 수집한다. 기존 스크립트에 기록 코드를 흩어놓지 말 것.
- 수집 시점은 기존 이벤트에 붙인다: `CurrencyManager.OnCurrencyChanged`(벽 배치), `PlayerHealth`(피해), `FogVisibility`(몬스터 최초 공개), `StageManager`(클리어·실패).
- 스테이지 종료 시 CSV 한 줄로 출력. 여러 번 플레이하면 줄이 쌓이게 한다.

### 10.4 결과 분석

기대값과 어긋나면 아래 순서로 조정한다.

| 결과 | 조정 방향 |
|---|---|
| 남은 재화가 계속 많음 | 스테이지 재화 총량을 줄이거나, 위협 타일 수를 늘림 |
| 클리어를 못 함 | 재화를 늘리거나 몬스터 공격력·쿨다운을 완화 |
| 반응 시간이 너무 짧음 | `visionRadius`를 키우거나 이동 속도를 낮춤 (세 컴포넌트 동기화 주의) |
| 반응 시간이 너무 김 | 반대로 조정 |

> 정량·정성 결과가 서로 엇갈릴 때는 **정성(플레이어 체감)을 우선**한다. 수치상 빠듯해도 플레이어가 고민하지 않았다면 의도가 전달되지 않은 것이다.
